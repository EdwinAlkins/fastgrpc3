# Benchmarks — 29/10/2026, dependencies

Cost of `Depends(...)` end to end, to choose where `def` providers run (audit point B1 / F4).
Raw data: `loop.json`, `threadpool.json` and their tables in `2026-10-29-deps/`.

## Setup

- Same machine and method as [the earlier runs](2026-10-29-protoruf-0.5.md): one server
  process on CPU 0, `ghz` on CPUs 2-7, 4 s per point; fastgrpc3 after `492081d`, protoruf
  0.5.1.
- Modes `fastgrpc3-deps-N-KIND` of `e2e_servers.py`: the echo handler takes N dependencies
  that do nothing, each a `sync` or `async` function or a `gen` / `agen` generator.
  `fastgrpc3` (no dependency) takes the fast path for plain unary methods.
- Two runs: providers on the event loop (`loop`), then `def` providers in a thread
  (`asyncio.to_thread`, prototype later shipped as `@blocking` / `sync_providers`).
  The baseline moved between the runs (4,528 then 4,747 requests/s): compare each run with
  its own baseline.

## Reading

- On the loop, dependencies are cheap: −5 % for the first one (the general path instead of
  the fast path), −7 % with 10; generators cost more (an exit stack per call): −19 % with 10.
  `def` and `async def` providers cost the same.
- A thread round trip costs about 60 µs per provider on one core (p50 at c=1: 0.18 ms
  without dependency, 0.24 ms with one `def` provider in a thread): −21 % with one provider,
  −58 % with 10, −69 % with 10 generators (enter and exit each cross threads).
- But a blocking provider on the loop stalls every call of the process: 4 concurrent calls
  with a 100 ms provider take 0.40 s on the loop, 0.10 s in threads.
- Decision (29/10/2026): providers run on the loop by default; `@blocking` sends one to a
  thread, `GrpcApp(sync_providers="threadpool")` sends every unmarked `def` provider,
  `@non_blocking` keeps one on the loop; a `def` provider holding the loop more than 10 ms
  is reported once in the log. Re-measured with that code: no visible cost from the check.
