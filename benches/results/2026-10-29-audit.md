# Benchmarks — 29/10/2026, after the audit fixes

Full suite after the audit fixes (lots 1 to 3) and the `validate=False` option. Raw data:
`codec.json`, `e2e.json`, `stream.json` (with the exact environment) and the tables in
`codec.md`, `e2e.md`, `stream.md` in `2026-10-29-audit/`.

## Setup

- Same machine and method as [the earlier runs](2026-10-29-protoruf-0.5.md): AMD Ryzen 7
  PRO 7840U laptop, frequency scaling on, Python 3.14.3; codec best of 7 rounds, end to end
  5 s per point, server alone on CPU 0, `ghz` on CPUs 2-7.
- fastgrpc3 after `f1ee459`, **protoruf 0.5.1**, grpcio 1.85.0, pydantic 2.14.1,
  protobuf 7.36.2, fastgrpc2 0.5.0.
- New mode `fastgrpc3-novalidate`: `GrpcApp(validate_requests=False)`, requests built
  without Pydantic validation (`model_construct` semantics, in Rust).

## Criteria (design doc 07)

| # | Criterion | Result | |
|---|-----------|--------|-|
| P1 | codec encode + decode ≥ 3× fastgrpc2 (medium) | 6.1 µs vs 25.3 µs: **4.2×** | met |
| P2 | codec at least as fast as upb + Pydantic | medium: encode 55×, decode 4.8× | met |
| P3 | end to end ≥ 1.3× fastgrpc2 (medium) | **1.18× / 1.22× / 1.23×** (c = 1 / 16 / 64); without validation 1.21× / 1.26× / 1.27× | not met (raw `grpc.aio` itself: 1.30–1.38×) |
| P4 | framework overhead < 15 % vs `grpc.aio` | small 5–6 %, medium 9–12 % | met |
| P5 | memory stable on long streams | 200,000 messages each way: +0.0 MiB | met |

## Validation off (`validate_requests=False`)

| requests/s | small c=16 | medium c=16 | large c=1 | large c=16 | large c=64 |
|---|---:|---:|---:|---:|---:|
| fastgrpc3 | 4,482 | 4,116 | 271 | 911 | 920 |
| fastgrpc3, no validation | 4,526 | 4,262 | 316 | 1,178 | 1,174 |
| gain | +1 % | +4 % | +17 % | +29 % | +28 % |

Decoding alone (codec bench): medium 5.01 → 2.74 µs, large 480 → 266 µs. The gain only
shows where validation weighs: on small and medium messages, `grpc.aio` takes most of a
call. Large messages reach 59 % of raw `grpc.aio` without validation (46 % with).

## Overhead against raw `grpc.aio`: same code, different days

This run reads 5 % (small) and 12 % (medium) at c=16, against 1 % and 2–7 % in the earlier
runs. Checked in the same session, alternating runs:

- protoruf 0.5.0 vs 0.5.1 under the same fastgrpc3: identical (fastgrpc3 at 90–91 % of
  raw, medium c=16);
- fastgrpc3 before the audit (`cb4d01b`) vs now (`f1ee459`), each with its own bench
  scripts: identical (small 96–98 %, medium 89–93 %, large 46 %).

So nothing regressed; the laptop's state (frequency, thermals) moves the ratio by several
points between sessions. Compare within one session only.

## Startup

`Schema.from_registry` + one codec per message, 10-field messages: 400 messages took
2,531 ms before (`ResolvedSchema.parent` rebuilt the set of message names at every call,
and every `MessageCodec` recomputed the conversion plans of the whole schema), 178 ms
after; 100 messages: 41 ms (linear).
