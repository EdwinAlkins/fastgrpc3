# Benchmarks — 29/10/2026

Raw data: `codec.json`, `e2e.json`, `stream.json` (with the exact environment) and the
tables in `codec.md`, `e2e.md`, `stream.md` in `2026-10-29/`.

## Setup

- AMD Ryzen 7 PRO 7840U laptop (8 cores / 16 threads, frequency scaling on: numbers are the
  best of 7 rounds for the codec, 5 s per point end to end), Linux, Python 3.14.3.
- fastgrpc3 0.1.0.dev0 (commit after `74fb409`), protoruf 0.4.0, grpcio 1.85.0,
  pydantic 2.14.1, protobuf 7.36.2 (upb), fastgrpc2 0.5.0.
- Messages (`benches/contract.py`): **small** (2 fields, 9 bytes), **medium** (20 fields,
  nested address, 3 lines, timestamp, enum, lists, 287 bytes), **large** (1,000 lines, 23 KB).
- End to end: unary echo; each server alone on CPU 0 (`taskset`), `ghz` on CPUs 2-7 with
  pre-encoded requests; `raw` = `grpc.aio` with upb messages (what generated stubs do), no
  framework. fastgrpc3 validates requests (Pydantic) in every run.

## Criteria (design doc 07)

| # | Criterion | Result | |
|---|-----------|--------|-|
| P1 | codec encode + decode ≥ 3× fastgrpc2 (medium) | 6.0 µs vs 25.4 µs: **4.2×** (encode 8.6×, decode 3.3×) | met |
| P2 | codec at least as fast as upb, conversion to Python included | medium: encode 55×, decode 4.9× faster than upb + Pydantic | met |
| P3 | end to end ≥ 1.3× fastgrpc2 (medium) | **1.20× / 1.25× / 1.24×** at concurrency 1 / 16 / 64 | not met (see below) |
| P4 | framework overhead < 15 % vs `grpc.aio` + stubs | small 0.1–1.3 %, medium 6.4–7.0 %, **with validation on** | met for small and medium |
| P5 | memory stable on long streams | 200,000 messages each way: server RSS flat (+0.0 MiB after warm-up) | met |

### Reading

- **P3 cannot be met on a medium message with `grpc.aio`**: even the raw server, with no
  framework and upb, is only 1.29–1.33× faster than fastgrpc2 there. Per call, `grpc.aio`
  itself takes ~210 µs of the ~230 µs fastgrpc3 spends; the codec is 6 µs. fastgrpc3 is at
  93 % of raw. The criterion is met for large messages (2.1× to 3.0×), where the codec and
  validation dominate.
- **Large messages are bound by validation**: decoding 1,000 lines takes 462 µs validated,
  257 µs in construct mode (no validation) and 22 µs for upb without Pydantic objects.
  fastgrpc3 still reaches 47 % of raw throughput there, against 16 % for fastgrpc2. A
  `validate=False` (construct) mode for trusted traffic is the next lever.
- The specialized fast path for plain unary methods (no context, hooks, middlewares or
  dependencies) brought small messages to raw's throughput and medium overhead from ~11 % to
  ~7 % (measured the same day, before / after).
