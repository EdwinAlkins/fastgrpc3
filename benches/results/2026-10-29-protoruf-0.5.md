# Benchmarks — 29/10/2026, protoruf 0.5.0

Same suite as [the earlier run](2026-10-29.md), after fastgrpc3 moved to protoruf 0.5.0
(`a5a683d`). Raw data: `codec.json`, `e2e.json`, `stream.json` (with the exact environment)
and the tables in `codec.md`, `e2e.md`, `stream.md`, `converted.md` in
`2026-10-29-protoruf-0.5/`.

## Setup

- Same machine as the earlier run: AMD Ryzen 7 PRO 7840U laptop (8 cores / 16 threads,
  frequency scaling on: numbers are the best of 7 rounds for the codec, 5 s per point end to
  end), Linux, Python 3.14.3.
- fastgrpc3 0.1.0.dev0 (`cb4d01b`), **protoruf 0.5.0**, grpcio 1.85.0, pydantic 2.14.1,
  protobuf 7.36.2 (upb), fastgrpc2 0.5.0.
- Messages (`benches/contract.py`): **small** (2 fields, 9 bytes), **medium** (20 fields,
  nested address, 3 lines, timestamp, enum, lists, 287 bytes), **large** (1,000 lines, 23 KB).
- End to end: unary echo; each server alone on CPU 0 (`taskset`), `ghz` on CPUs 2-7 with
  pre-encoded requests; `raw` = `grpc.aio` with upb messages, no framework. fastgrpc3
  validates requests (Pydantic) in every run.

## Criteria (design doc 07)

| # | Criterion | Result | |
|---|-----------|--------|-|
| P1 | codec encode + decode ≥ 3× fastgrpc2 (medium) | 6.1 µs vs 25.3 µs: **4.1×** (encode 8.4×, decode 3.2×) | met |
| P2 | codec at least as fast as upb, conversion to Python included | medium: encode 56×, decode 4.6× faster than upb + Pydantic | met |
| P3 | end to end ≥ 1.3× fastgrpc2 (medium) | **1.25× / 1.29× / 1.28×** at concurrency 1 / 16 / 64 | not met (see below) |
| P4 | framework overhead < 15 % vs `grpc.aio` + stubs | small −3.4 to 5.3 %, medium 1.7–4.8 %, **with validation on** | met for small and medium |
| P5 | memory stable on long streams | 200,000 messages each way: server RSS flat (+0.0 MiB after warm-up) | met |

### Reading

- **The three benchmark messages do not use what protoruf 0.5 changed**, so the codec numbers
  are the earlier run's within noise (medium decode 5.06 µs vs 4.98, large 467 vs 462).
  0.5 moved renamed fields (`proto_name=`), aliases and `datetime.date` from a Python dict
  conversion into the Rust codec; the next section measures those.
- **End to end, the differences with the earlier run are noise.** Medium overhead reads
  1.7–4.8 % here against 6.4–7.0 % in the earlier run, and small messages at c=64 come out
  faster than raw; nothing in the medium message's path changed, and large messages at c=1
  lost 18 % on raw and fastgrpc3 alike (frequency scaling). Treat P4 as "a few percent" on
  small and medium messages.
- **P3 still cannot be met on a medium message with `grpc.aio`**: the raw server is itself
  only 1.27–1.34× faster than fastgrpc2, and fastgrpc3 sits at 95–98 % of raw. Large
  messages: 1.7× to 3.1× fastgrpc2, bound by validation (fastgrpc3 at 47–61 % of raw).

## Renamed fields, aliases and dates (protoruf 0.4.0 vs 0.5.0)

An eight-field message with three nested lines, in four variants: plain, one field renamed
with `field(8, proto_name="from")`, one field with `alias="orderNumber"`, one
`datetime.date` field. Measured with fastgrpc3 `effa0e5` + protoruf 0.4.0 and `cb4d01b` +
protoruf 0.5.0, two runs each, µs per message (`2026-10-29-protoruf-0.5/converted.md`):

| | 0.4.0 encode | 0.4.0 decode | 0.5.0 encode | 0.5.0 decode |
|---|---:|---:|---:|---:|
| plain | 0.53 | 2.95 | 0.53 | 3.05 |
| renamed field | 0.72 | 3.38 | 0.55 | 3.08 |
| alias | 0.54 | 3.26 | 0.53 | 3.11 |
| `date` | 0.89 | 3.75 | 0.53 | 3.17 |

With 0.4.0, a renamed field cost +36 % on encode and +15 % on decode, a date +68 % and
+27 %; with 0.5.0 these models cost the same as a plain one. Only the JSON carrier (D7) and
`proto_enum` mappings still take the converted path.
